# WarSampo baseline record: 2026-09-01

This record supersedes the initial 2026-08-31 baseline after the rule and fail-closed behavior review. The `warsampo/` checkout is intentionally ignored by Git, so the committed baseline contains stable signatures while this document preserves the corpus selection and runtime context used to generate them. The complete baseline below was generated after applying the reviewable [invalid-date correction proposal](../../proposals/source-corrections/2026-09-01-invalid-dates/README.md) to the local snapshot.

## Environment

- WarSampo snapshot present in the repository workspace on 2026-09-01
- 61 RDF source files, approximately 679 MB and 15.5 million Turtle lines
- Apache Jena 6.2.0 on Eclipse Temurin Java 21
- Docker/OrbStack on macOS, `-Xmx4g`
- generated role-aware manifests for RDF, RDFS, OWL, SKOS, and DCMI Terms

Strict parsing found two invalid calendar dates in `warsampo/warsa-event-data/times.ttl`: `1939-12-35` and `1940-02-30`. The correction proposal reuses the corroborated December 22–23 Parissavaara span and represents the unresolved February start as unknown while retaining its March 3 upper bound. With that proposal applied locally, all 61 sources parse and participate in validation. The linter still fails closed and suppresses report or baseline publication if any malformed input reappears.

Fifteen vocabulary findings are the exact, automatically repairable misspellings documented in ADR-001. The remaining finding uses the DCMI namespace resource itself as an RDF class; it has no automatic repair because the intended class is ambiguous. Generated RDF container-membership properties such as `rdf:_1` are accepted, while declarations of misspelled standard terms are checked in addition to predicate and class uses. Multiple offending values on one subject retain their full finding multiplicity.

The profile no longer asserts that every subject of CIDOC CRM `P4_has_time-span` is an event with at most one time span. WarSampo uses the property on other resource kinds, including war-diary documents with multiple periods, and neither the schema nor an accepted project requirement supplied that cardinality. Removing the unsupported rule eliminated 110 false violations. Reflexive `skos:broader` and `skos:related` statements are legal SKOS and are now warnings rather than violations.

The committed `baselines/warsampo-local.tsv` uses baseline format v2. It contains only violations. Signatures exclude result-message wording and include the SHACL constraint component plus deterministic occurrence indexing, preserving duplicate blank-node findings without tying accepted findings to prose.

## Cross-module audit

`--cross-module` applies the 16 local rules per module, streams successfully parsed graphs into TDB2, and, only after every source parsed successfully, runs union validation. Six reusable SKOS rules are re-evaluated over the union so cycles, label conflicts, and relation conflicts split across files are visible. Four explicitly union-scoped rules also run:

- duplicate identifiers;
- unresolved internal references;
- unresolved or untyped event participants; and
- birth/death chronology.

Union results already present locally are de-duplicated. Fixture coverage verifies a SKOS cycle whose two edges live in separate files and verifies that no `@union` finding is produced after any parse failure.

After adding per-rule timings and aggregating the life-event chronology join by person, the full union audit completed in 390,133 ms with a 2,369.0 MiB sampled heap peak. It found 1,643 new violations and 379 new warnings beyond this module-local baseline. The complete performance and finding breakdown is recorded in the [cross-module audit record](./2026-09-01-warsampo-union.md). Module-local validation remains the normal corpus regression path until the union findings are reviewed and the two million-node label checks are made suitable for frequent CI use.

## Review policy

The baseline is not a declaration that its findings are correct data. It records known violations so new violations can fail regression checks independently of existing cleanup work. Warnings are never baselined. Remove an entry only when the corresponding source issue is fixed or the rule or severity decision is deliberately changed and reviewed.
